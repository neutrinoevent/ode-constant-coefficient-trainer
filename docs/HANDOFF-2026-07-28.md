## 1. What the app is

A drill trainer for the case structure of constant-coefficient linear ODEs, at
the level of Zill, *A First Course in Differential Equations*, 9e, chapter 4.
Static site, local-first, no server and no accounts. Progress in `localStorage`.

- 73 stated results in 9 families, covering §4.1–§4.7 plus §5.1
- 18 problem generators (12 multiple choice, 6 typed)
- a 15-step guided path
- 9 tabs: Path, Learn, Classify, Solve, Challenge, Cards, Progress, About, Settings

The material is small — three root cases, one multiplication rule, a handful of
operator identities — and the skill is recognition speed. Everything is built
around that.

## 2. The three load-bearing ideas

Read these before touching anything. Everything else is downstream.

### 2.1 A general solution is a span, not a string (`src/lib/answer.ts`)

There are infinitely many correct ways to write a fundamental set.
`c1*cosh(x) + c2*sinh(x)` is exactly as correct as `c1*e^x + c2*e^(-x)`.
So `checkSpan` never compares text. It:

1. parses with mathjs and collects the free symbols acting as arbitrary constants;
2. isolates the function multiplying each one by evaluating with that constant at
   1 and the rest at 0;
3. samples each on a window and asks whether it lies in the span of a correct
   fundamental set (least-squares residual against an orthonormalised basis,
   tolerance `1e-6`);
4. asks whether there are exactly *n* of them and whether they are independent
   (rank of the sampled columns, same tolerance).

Together: span **equality**. Consequences worth keeping:

- any valid fundamental set passes, including recombinations nobody anticipated;
- `c1*e^(2x) + c2*e^(2x)` fails as **linearly dependent** — the real reason —
  rather than as a string mismatch;
- the same code grades a trial form with `A, B, C, …` instead of `c₁, c₂, …`;
- Cauchy–Euler reuses it by passing raw functions (`x^m`, `x^m ln x`) instead of
  quasipolynomial terms, sampled on `x > 0`.

Linearity in each constant is checked explicitly (doubling a constant must double
its contribution), which is what catches `c1*c2*e^(3x)`.

Constants: sampling window `[-1.1, 1.3]`, 37 points; Cauchy–Euler `[1.15, 3.4]`.

### 2.2 Exact arithmetic where exactness is available (`src/lib/quasipoly.ts`)

Sampling is right for grading a student. It is wrong for verifying the app's own
corpus, where a numerical near-miss would silently ship a wrong answer.

`quasipoly` implements finite sums of `c·x^k e^{ax} cos(bx)` and its sine
partner. That family is **closed under differentiation**, so applying a
constant-coefficient operator to one is exact arithmetic. Every object the app
quizzes on lives there: solution bases, forcing functions, trial forms, and the
residual after an annihilator.

`src/lib/frac.ts` adds exact rationals for one job: multiplying out a
characteristic polynomial from its roots and clearing denominators, so the
printed equation and its stated roots can never disagree — including for
half-integer roots that give a leading coefficient of 2 or 4.

The corpus test uses both: it applies each problem's stated operator to each
stated basis function and requires **exactly** zero.

### 2.3 The root set is the single source of truth (`src/lib/roots.ts`)

A generated problem is built from a `RootSet` — real roots and conjugate pairs,
each with a multiplicity. Everything else is *computed* from it:

```
RootSet ─┬─ charPoly()             → integer coefficients
         ├─ odeTex()               → the printed equation
         ├─ charEqTex()            → the auxiliary equation
         ├─ factoredTex()          → the factored form
         ├─ rootsTex()             → the root list
         ├─ basisTerms()           → the fundamental set graded against
         ├─ generalSolutionTex()   → the displayed answer
         ├─ generalSolutionText()  → the exemplar the corpus test types in
         ├─ caseOf()               → the case label
         ├─ deriveHomogeneous()    → the worked example
         └─ RootPlane              → the complex-plane plot
```

Nothing is stored alongside. The equation on screen cannot disagree with the
answer being graded, because they are the same object rendered twice. **Preserve
this.** If you find yourself storing a rendered string next to the roots that
produced it, that is the invariant breaking.

## 4. The answer checker, in more detail

`checkSpan(raw, target, opts)` returns `{ ok: true, constants }` or
`{ ok: false, code, message }`. The codes are the diagnosis, and each has its own
message:

| code | means |
|---|---|
| `empty` / `parse` / `symbol` | could not read it — **not scored as wrong** |
| `domain` | did not evaluate on the window — **not scored as wrong** |
| `no-constants` / `too-few` / `too-many` | wrong number of arbitrary constants |
| `stray` | a term with no arbitrary constant attached |
| `nonlinear` | a constant multiplying another constant, not a function |
| `outside` | one piece does not solve the equation |
| `dependent` | the pieces are not independent |

Solve treats the first four as unscored: a syntax slip is not a wrong answer.
That rule lives in `Solve.tsx`, in the `scorable` computation.

Input preprocessing (`preprocess`) handles `ln → log`, `c_1 → c1`, `{}` → `()`,
and implicit multiplication (`2x`, `3sin(`, `)(`, `c1cos(2x)`). It uses
`mathjs/number`, the number-only build — same parser and elementary functions
without the BigNumber/Complex/Matrix machinery, which cut ~280 kB.

Annihilators take a different path: `parseOperator` (recursive descent over
`expr := term (('+'|'-') term)*`, juxtaposition as multiplication) yields an
integer polynomial in `D`, and `gradeAnnihilator` applies it to `g` exactly. Any
operator that kills `g` is accepted; a non-minimal one is accepted **with a note
naming the minimal order**, not marked wrong.

## 5. The path, in more detail

`PATH` is 15 steps. A step is:

```ts
{ id, title, goal, section, teach?, practice: PracticeItem[], run: {length, pass}, scope }
```

`PracticeItem` is `{kind:'generator', generatorId, variant?}` or
`{kind:'cases', familyId}`. **A step owns no questions of its own** — it points
at generators and families that already exist. Adding a generator makes it
reachable from free practice immediately and from a step by adding one line.

The steps, in order:

```
1  p-exponential     Why an exponential          §4.3
2  p-roots           Read the roots              §4.3
3  p-case-1          Case I — distinct real      §4.3   ← pinned to one case
4  p-case-2          Case II — repeated          §4.3   ← pinned
5  p-case-3          Case III — complex pair     §4.3   ← pinned
6  p-mixed           Tell them apart             §4.3   ← first mixing
7  p-behaviour       What the roots mean         §4.3
8  p-reverse         Backwards                   §4.3
9  p-higher          Higher order                §4.3
10 p-structure       Adding a forcing term       §4.1
11 p-trial           Guessing the shape of y_p   §4.4   ← 'plain' forcing
12 p-multiplication  The multiplication rule     §4.4   ← 'resonant' forcing
13 p-annihilator     Annihilators                §4.5
14 p-varpar          When the guess will not work §4.6
15 p-cauchy          Cauchy-Euler                §4.7
```

Steps 3–5 are the whole point of v2: one case at a time, in isolation, before
step 6 mixes them. That is where v1 started, and starting there is why the cases
never formed as categories.

**The pinning mechanism.** `GeneratorDef.generate(rng, variant?)`. A generator
declares `variants: readonly string[]`; one that does not understand a variant
ignores it. `secondOrder(rng, kind)` already took a case argument, so this was
plumbing, not new mathematics.

- case pinning (`distinct` / `repeated` / `complex`): `case-2`, `roots-only`,
  `general-2-choice`, `general-2`
- resonance pinning (`plain` / `resonant`): `trial-form`, `trial-choice`,
  `shift-s`

**Known compromise.** A path run is multiple choice throughout, so it never
switches answer interfaces mid-run. Steps naming a typed generator are served its
choice sibling via `choiceFallback` in `Path.tsx`. Typing lives in Solve. This is
open question 4 below.

**Gating is soft, deliberately.** All nine tabs are open from first launch. The
path is the default view and the coach points at it, but nothing is locked.
`level: 'advanced'` (placement answer "revising for an exam") skips it as the
landing view. Rationale in `VISION.md` D12.

## 6. Invariants, and which test guards each

Break one of these and something ships wrong. Each is guarded; know which.

| Invariant | Guard |
|---|---|
| Every generated problem agrees with its own stated answer | `corpus.test.ts` — exemplar must pass the real grader, 200 seeds per generator |
| A stated fundamental set is exactly annihilated by its stated operator | `corpus.test.ts` — `applyOperator` must return exactly zero |
| A stated basis is numerically independent on the sample window | `corpus.test.ts` — `orthonormalize` must return full rank |
| Every MCQ has ≥3 distinct options with exactly one correct | `corpus.test.ts` |
| Explanations stay aligned with their options through shuffling and trimming | `corpus.test.ts` — lengths match, correct option carries `null` |
| Every derivation has ≥4 labelled, non-empty steps, first and last with math | `corpus.test.ts` |
| Every generator and family a path step names exists | `path.test.ts` |
| Every variant a step asks for is actually offered | `path.test.ts` |
| Pinning really narrows — `repeated` always yields a factor of `x` | `path.test.ts`, 40 seeds |
| Pass marks are reachable and not free | `path.test.ts` |
| The grader accepts equivalent fundamental sets and rejects near-misses | `answer.test.ts` |
| The operator parser round-trips and rejects malformed input | `answer.test.ts` |
| Every tab mounts; a question can be answered; diagnosis and derivation surface | `App.ui.test.tsx` |

**The UI tests sample.** They draw random questions and loop until they find one
with the property under test. If you add a generator whose problems lack a
derivation or explanations, those loops get slower, and if you add enough of
them they will eventually fail on the iteration cap. That is intended pressure.

## 7. Recipes

### Add a generator

Module in `src/generators/`, export a `GeneratorDef`, register in `index.ts`.

```ts
{
  id: 'my-generator',
  name: 'Shown in Learn and Progress',
  blurb: 'One line.',
  section: '§4.3',
  topicId: 'roots2',            // a family id from data/cases.ts
  mode: 'entry',                // or 'choice'
  variants: SECOND_ORDER_KINDS, // optional
  generate: (rng, variant) => ({ ... }),
}
```

- typed problems **must** supply `answer.exemplar` (one answer that passes) and,
  where there is one, the homogeneous `operator` — the corpus test uses both;
- supply `derivation: () => deriveHomogeneous(roots)` and "Show me how" appears
  everywhere the problem does;
- build wrong options as `{ tex, why }` and pass them through `choiceAnswer` —
  bare strings still work but teach nothing.

### Add a path step

One object in `PATH`. `teach.body` paragraphs are rich text; `teach.example` is a
thunk returning derivation steps, built from a **fixed** root set so the teaching
screen is stable. `path.test.ts` will reject a dangling pointer or an unsupported
variant.

### Add a stated result

One entry in the relevant family in `data/cases.ts`. `traps` should be real
mistakes; they become MCQ distractors and are the difference between a
distractor that teaches and filler.

### Add a challenge mode

Needs a stable id in `data/challenges.ts` so progress survives export/import, and
a `topicId` so it feeds family mastery.

## 8. Known rough edges

Honest list. None is blocking.

1. **Bundle is 969 kB (290 kB gzipped).** mathjs is most of it, and only `Solve`
   needs it. A dynamic import behind that tab would roughly halve the initial
   load. Already on the backlog; the reason it was not done is that `answer.ts`
   is imported by tests too and the split needs care.
2. **`initial-prompt.txt` is untracked but present.** Intentional. If the repo is
   ever re-cloned fresh, it will not come back.
3. **A single-group annihilator derives in exactly four steps.** This bit once:
   a UI assertion used `> 4` where the corpus contract is `>= 4`, and the test
   was flaky depending on which question was drawn. Fixed 2026-07-28. If you
   change `deriveAnnihilator`, keep four as the floor or update both tests.
4. **`Path.tsx` is 422 lines** and holds three screens (overview, teach, run).
   It is the most likely file to want splitting.
5. **Vitest prints a `--localstorage-file` warning** on every run. Harmless
   jsdom/node noise, not a project problem.
6. **The corpus test runs 200 seeds × 18 generators** and takes ~3 s. If it gets
   slow, lower `SEEDS` rather than dropping assertions.
7. **`src/.DS_Store` exists on disk** and is gitignored.

## 9. Open questions, with my current read

From `VISION.md`, restated with an opinion so a cold start is not neutral.

1. **Should Solve accept complex-exponential form for Case III?**
   `c1*e^((-1+2i)x) + c2*e^((-1-2i)x)` is a correct fundamental set over ℂ and
   the real-valued sampling rejects it. Currently deliberate — the section is
   about producing the real form. *My read: keep rejecting it, but say so in the
   UI. A silent rejection of a correct answer is the worst version of this.*
2. **Should the harder default kick in per-topic rather than globally?**
   Withholding `y_c` is a global toggle. *My read: yes, tie it to the tier — once
   a topic is Proficient, stop showing it. But this needs the tier to be trusted
   first, which argues for doing it after some real use.*
3. **Does §5.1.3 (forced motion, resonance) belong?** *My read: no. Damping is in
   scope because it is the same three cases. Resonance is a different idea and
   pulls the app into chapter 5 proper.*
4. **Should a path run include typed answers?** Currently choice-only (see §5).
   *My read: this is the most valuable open question. The span checker is the
   better instrument and it is absent from the guided route. The natural shape is
   faded worked examples — study, then completion with the last step blank, then
   solve — which would also close the gap in one move.*
5. **Should a step clear on a criterion rather than one good run?** Pass marks
   are fixed counts (5 of 6, 7 of 8). *My read: a single run is a weak signal.
   Tier-based clearing is more honest but risks stalling someone. Compromise:
   clear on one good run, but mark the step "needs another look" if the tier
   later drops.*

## 10. Backlog, prioritised

My ordering, not a commitment. Full list in `VISION.md`.

**High value, low cost**
- Timed mode. Recognition *speed* is the actual target and nothing measures it.
  A per-question clock feeding a separate fluency statistic, distinct from
  accuracy.
- Code-split mathjs behind Solve.
- Surface which mistake a distractor represents in `Learn` too, not only after a
  wrong answer.

**High value, real cost**
- Initial-value problems. Given an ODE and conditions at a point, solve for the
  constants. Needs a second checker (a specific function, not a span) — but the
  exact solution is computable in the quasipolynomial algebra once the linear
  system for the constants is solved, so most machinery exists.
- Typed answers inside a path run / faded worked examples (open question 4).
- The three-cases explorer: one figure, `b` on a slider, discriminant sign →
  roots moving on the plane → solution form → solution curve. `RootPlane` is
  half of it. Deferred twice on purpose: highest chance of making it click,
  highest chance of ending up decorative. Best judged after real use.

**Lower priority**
- Boundary-value problems where existence or uniqueness fails (§4.1.1) — the
  instructive case, currently absent.
- Higher-order Cauchy–Euler (brings `(ln x)²`).
- Superposition drill: `g = g₁ + g₂` with different resonance on each piece.
- Wronskian as a typed answer.
- Goal tracking in the style of kanji-trainer V-001 D5.
- Per-step review of missed questions.
- Print/export a problem set with an answer key.
